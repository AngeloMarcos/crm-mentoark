# Auditoria de Código — Log

### 🔴 GRAVE: IA respondia sem estar configurada, com prompt de outro cliente ("Cris") por padrão (2026-07-28)

**Contexto:** usuário reportou o achado mais grave até agora nesta série de auditorias: um cliente novo tinha a IA já ativa e respondendo, usando o prompt/persona configurado para "Cris" — uma cliente real da Mentoark. Investigação a fundo encontrou uma cadeia de 3 bugs que se somavam, não um só.

**🔴 Causa 1 — `agent_configs.ativo` nascia `true` por padrão em 3 pontos de criação automática de linha:** `POST /api/agent-config` (`backend/src/routes/agent-config.ts`, `ativo ?? true` no INSERT do UPSERT), `reconciliarInstanciasEvolution()` (`backend/src/services/evolutionReconciliation.ts`, INSERT disparado sempre que uma instância Evolution nova é detectada aberta para um tenant) e `syncEvolution()` (`backend/src/routes/integracoes.ts`, disparado ao conectar/verificar integração na tela de Integrações). Em todos os 3, a linha nascia com a IA ativa antes de qualquer prompt real existir. **🔧 Corrigido:** os 3 agora usam `false` como default. Confirmado que nenhum dos `ON CONFLICT DO UPDATE` correspondentes toca a coluna `ativo` — o fix só afeta a criação inicial da linha, nunca desliga um agente que o usuário já ativou de propósito depois.

**🔴 Causa 2 — `agentEngine.ts` respondia mesmo sem nenhum prompt configurado.** Sem `agent_configs.prompt_sistema` nem um fallback real em `agent_prompts`, o motor caía num prompt genérico hardcoded ("Você é um assistente prestativo.") e respondia mensagens reais mesmo assim — violando diretamente a regra "a IA não pode responder sem antes estar configurada". **🔧 Corrigido:** sem prompt real de nenhuma das duas fontes, o motor agora recusa e não responde (mesmo comportamento já usado para "agente não encontrado" mais acima na mesma função).

**🔴 Causa 3 (a mais grave, explica o nome "Cris" especificamente) — `ConfigAgenteIA.tsx` tinha `nome_agente: "Cris"` hardcoded como default do formulário, com `ativo: true`, E a tela era completamente não-funcional.** `carregarConfig()`/`salvar()` chamavam `api.from("agent_configs").select()/.insert()/.update()` — o QueryBuilder genérico monta a URL a partir do nome da tabela (`/api/agent_configs`, com underscore, plural). Essa rota **nunca existiu** no backend — grep exaustivo em `backend/src/index.ts` e todo `backend/src` confirma que só existe `/api/agent-config` (singular, hífen, rota própria em `agent-config.ts`, montada em `index.ts:324`). Toda tentativa de carregar a config sempre voltava 404 — e o `error` do load nunca era checado (`if (data) setConfig(data)`, sem `else`), então a falha era **completamente silenciosa**: a tela ficava presa exibindo o `defaultConfig` inicial (nome "Cris", ativo) como se fosse uma configuração real, salva e carregada do banco, para qualquer cliente novo cuja config nunca tivesse sido preenchida de verdade. (O `salvar()` até checava `error`, mas isso não ajuda se o operador nunca percebe que o "carregado" já era falso.) Confirmado ainda que, mesmo corrigindo só a URL, o formato de resposta segue incompatível: a rota real devolve um objeto único (`res.json(r.rows[0] ?? null)`), enquanto o `_exec()` do QueryBuilder para `.maybeSingle()` espera um array (`data[0]`) — um fix parcial de URL sozinho continuaria retornando `null`.

**🔧 Corrigido:**
- `defaultConfig`: `nome_agente: ""` (era `"Cris"`) e `ativo: false` (era `true`).
- Dois placeholders de exemplo que ainda citavam "Cris" (saudação inicial e campo "Nome do Agente") trocados para um nome fictício ("Sofia").
- `carregarConfig()`/`salvar()` reescritos para chamar `api.get('/api/agent-config')`/`api.post('/api/agent-config', config)` — os helpers simples do client (não o QueryBuilder de tabela) — batendo na rota real, que já faz UPSERT por `user_id` no backend. Simplifica também a lógica de `salvar()`: não precisa mais decidir entre insert/update via `config.id`, já que o backend sempre faz UPSERT.

**Build:** backend (`swc`) e frontend (`vite build`) limpos.

**NÃO corrigido — decisão do usuário necessária:** qualquer tenant já contaminado no banco (uma linha real de `agent_configs` com `nome_agente='Cris'` e/ou o conteúdo verdadeiro do prompt dela, pertencente a outro `user_id`) continua contaminado — este fix impede o problema de se repetir daqui pra frente e impede a IA de responder enquanto não configurada corretamente, mas não reescreve dados já existentes. Uma correção em lote (identificar contas com `nome_agente='Cris'` que não sejam a conta real da Cris, resetar `prompt_sistema`/`ativo`) é uma escrita em produção e não deve ser feita sem confirmação explícita do usuário, por protocolo. Também não foi determinado o mecanismo exato pelo qual o prompt REAL de Cris (conteúdo, não só o nome no formulário quebrado) chegou a ficar persistido na conta do cliente novo — pode ter sido um caminho automatizado ou erro humano de operador habilitado por esta mesma UI quebrada; vale confirmar com o usuário o que exatamente está gravado hoje na linha `agent_configs` do cliente afetado antes de decidir a correção.

**Deploy:** pendente — dada a severidade, homolog primeiro, produção só após validação explícita do usuário.

### 🔴 Grupos sempre sem nome/foto real + contato novo podia herdar o nome do próprio usuário (2026-07-28)

**Contexto:** usuário reportou (1) fotos de perfil ainda faltando em alguns casos e (2) quase todos os grupos aparecendo como número em vez do nome real do WhatsApp. Investigação encontrou dois bugs distintos, ambos em `webhook.ts`/`whatsapp.ts`.

**🔴 Achado 1 — grupos NUNCA tiveram nome/foto real buscados, em lugar nenhum do sistema.** Confirmados 3 pontos que excluem grupo explicitamente: upsert de contato em `webhook.ts` (`if (!isGroup) {...}`, 2 ocorrências), o JOIN da query `GET /conversas` (`AND NOT r.is_group`), e o botão "Sincronizar fotos de perfil" (`remote_jid NOT LIKE '%@g.us'`). `whatsapp.ts` sempre sintetiza `Grupo ${últimos dígitos do JID}` como nome — não é falha intermitente, é comportamento garantido pra 100% dos grupos. Causa raiz mais profunda: `payload.data?.pushName` (usado como "nome" em geral no arquivo) é sempre o pushName de quem MANDOU aquela mensagem específica — pra grupo, isso é a pessoa que escreveu, nunca o "subject" do grupo (esse é um conceito separado, só existe via endpoint dedicado da Evolution).

**🔧 Corrigido:** nova função `buscarInfoGrupo()` (`whatsappMediaStorage.ts`) chama `GET /group/findGroupInfos/{instance}?groupJid=...` (Evolution API v2 — confirmado documentação oficial + [evolution-api#2124](https://github.com/EvolutionAPI/evolution-api/issues/2124), que também documenta que uma minoria de grupos pode voltar sem subject/foto mesmo assim — tratado como falha suave, cai no fallback "Grupo XXXX" já existente, sem regressão). Usada em dois lugares: (a) `webhook.ts`, organicamente a cada mensagem nova de grupo (match exato de `telefone`, não `ILIKE` por sufixo de 11 dígitos — JID de grupo é um ID arbitrário longo, não um telefone BR, sufixo de 11 dígitos criaria risco de colisão entre grupos); (b) `POST /api/whatsapp/sync-profiles` (botão "Sincronizar fotos de perfil"), backfill de grupos já existentes sem precisar esperar mensagem nova. `GET /conversas` (`whatsapp.ts`) ganhou uma CTE separada (`grupo_unico`, match exato) e agora prioriza nome/foto reais quando já sincronizados, mantendo "Grupo XXXX"/sem foto como fallback pros ainda não sincronizados.

**🔴 Achado 2 — contato novo podia herdar o nome do PRÓPRIO usuário da conta.** No upsert antecipado de contato (`webhook.ts`, roda ANTES do branch `if (fromMe)`), `pushName` era usado pra `nome`/`push_name` sem checar se a mensagem era `fromMe:true` — se o PRIMEIRO evento associado a um contato novo fosse uma mensagem enviada pelo próprio atendente/CRM (ex: iniciar conversa nova, disparo), e a Evolution devolvesse o nome de perfil do dono da instância nesse campo (comportamento observado na prática pelo usuário, não documentado explicitamente na Evolution), o contato ficava com o nome do usuário gravado — e a guarda existente ("só sobrescreve nome se nome==telefone") nunca desfaz isso depois, mesmo quando o contato responde de verdade (uma vez contaminado, fica contaminado). Mesmo padrão encontrado numa segunda INSERT dentro do próprio branch `if (fromMe)` (linha do fluxo "pausar IA pra novo contato").

**🔧 Corrigido (daqui pra frente):** `pushName` só é usado pra identidade de contato quando `!fromMe`; pra mensagem enviada, cai no mesmo placeholder seguro (`telefone`/`null`) já usado em outros pontos do arquivo. **NÃO corrigido — contatos JÁ contaminados no banco continuam com o nome errado** (o guard "só corrige se nome==telefone" não alcança mais essas linhas, já que nome != telefone depois da contaminação). Precisa de decisão do usuário: uma correção em lote exigiria comparar `contatos.nome` contra o `profileName` real da instância conectada (via Evolution) e resetar só as linhas que baterem exatamente — escrita em produção, não implementada sem confirmação explícita, por protocolo.

**Build:** backend (`swc`) limpo. **Não testado com Evolution real nesta sessão** — deploy em homolog primeiro, usuário validar com um grupo e um contato novo reais antes de produção.

### 🔴 Envio de mídia do composer do chat (imagem/vídeo) nunca funcionou — causa raiz confirmada e corrigida (2026-07-28)

**Contexto:** usuário reportou não conseguir enviar imagem nem vídeo pelo composer do chat WhatsApp, e também não conseguir colar (`Ctrl+V`) um print da tela.

**Causa raiz (envio de mídia):** `enviarMidia()` (`WhatsAppInterface.tsx`) mandava o arquivo anexado como `data:<mime>;base64,<payload>` inteiro no campo `mediaUrl`, e `POST /api/whatsapp/send` (`whatsapp.ts`) repassava essa string sem alteração pro campo `media` do payload da Evolution API — sem stripar o prefixo `data:...;base64,` (que contém caracteres fora do alfabeto base64, corrompendo a decodificação) nem informar `mimetype` separado. Levantamento em todo o repositório: **nenhum outro envio de mídia do sistema manda base64 cru pra Evolution** — `disparoProcessor.ts` (imagem/áudio/documento de campanha) e `agentEngine.ts` (resposta em voz TTS) sempre fazem upload prévio do arquivo e mandam uma URL http(s) estável. Ou seja, o composer do chat era o único caminho tentando um padrão sem nenhum precedente comprovado de funcionar contra essa API.

**🔧 Corrigido:** nova rota `POST /api/whatsapp/upload-media` (mesmo padrão multer+`UPLOADS_DIR`+`/uploads` já usado por `catalogo.ts`/`galeria.ts`) — recebe o arquivo via multipart, resolve extensão via `extensaoParaArquivo()` (agora exportada de `whatsappMediaStorage.ts`, usa nome→mimetype→categoria como fallback, importante porque um print colado via paste não tem nome de arquivo real) e salva em `UPLOADS_DIR`, devolvendo uma URL estável. `enviarMidia()` agora faz esse upload primeiro e manda a URL resultante pro `/send`, em vez do data URI — `dataUrl` continua existindo só pro preview otimista local (`<img>`/`<video>` renderizam direto sem precisar do proxy autenticado).

**Também corrigido — "não consigo colar um print":** não existia handler de paste no composer nenhum — colar uma imagem da área de transferência não fazia nada, único jeito de anexar era o seletor de arquivo do SO. Extraído `attachFile()` de `handleFileSelected` (mesma validação de tamanho/preview) e adicionado `handlePasteImage` (novo) no `onPaste` do textarea principal — procura o primeiro item de imagem em `clipboardData.items` e reaproveita o mesmo `attachFile()`, sem duplicar lógica.

**Build:** frontend (`vite build`) e backend (`swc`) limpos. `tsc --noEmit` (checagem estrita, separada do build real) não completou nesta sessão por falta de memória do Node na máquina local (heap OOM em ambos os projetos, mesmo sem tocar neles) — não é um sinal de erro no código, é limitação do ambiente; `npm run build` (o mesmo gate que `scripts/deploy.sh` usa) passou limpo nos dois. **Nada testado com Evolution real ainda** — sem acesso a WhatsApp conectado nesta sessão; precisa de validação manual em homolog antes de produção.

### 🔴 Auditoria pré-Disparos: client.ts sem o fix de 25/07 em PRODUÇÃO + segundo bug de filtro perdido (2026-07-27)

**Contexto:** usuário ia rodar disparos de verdade em homologação (listas já importadas) e pediu para confirmar que o motor não manda tudo de uma vez (risco de bloqueio do WhatsApp) antes de prosseguir.

**Motor de disparo (`disparoProcessor.ts`) — revisado, sem bug novo encontrado.** Já tem: lote de 5 processado sequencialmente (nunca em paralelo), delay aleatório entre CADA mensagem por perfil (`safe` 30-60s / `moderate` 15-30s / `fast` 5-15s), trava singleflight no `setInterval` de 2s do `index.ts` (impede dois lotes rodando ao mesmo tempo), teto diário configurável (500 padrão) com auto-pausa, circuit breaker de erros consecutivos, janela de horário comercial + pausa de fim de semana, round-robin real entre instâncias selecionadas. Confirma que o desenho já é conservador — motivo real de preocupação era outro (achados abaixo). Endpoint legado `POST /disparos/enviar` (rate limit mais fraco, 1 msg/s) confirmado **não usado por nenhuma tela hoje** — código morto, sem risco atual, candidato a remoção futura.

**🔴 Achado 1 — `src/integrations/database/client.ts` em PRODUÇÃO ainda tinha o bug de `.select()` corrigido em 25/07 (commit `8e5a42d`).** Confirmado via `stat` na VPS: `/opt/crm/src/integrations/database/client.ts` com mtime de 10/07 (pré-fix), enquanto `/opt/crm-homolog/.../client.ts` já tinha mtime de 25/07 (pós-fix) — homolog recebeu o fix em algum deploy anterior não documentado explicitamente no `STATUS.md`, produção nunca recebeu. Isso é exatamente o padrão usado por `StepReview.handleStart` em `Disparos.tsx` pra criar a campanha (`api.from("disparos").insert(payload).select().single()`) — em produção, "Iniciar Disparo" hoje criaria um GET silencioso em vez de POST, e a campanha nova nunca existiria: `campaignData.id` seria o id de uma linha `disparos` ARBITRÁRIA já existente, e todos os `disparo_logs` da campanha nova seriam inseridos com esse id errado. Homologação já estava correta (confirma por que a importação de listas do usuário funcionou lá). **Não corrigido ainda em produção nesta sessão** — deploy pendente, ver `STATUS.md`.

**🔴 Achado 2 — novo, mesma classe do Achado 1: `.not()`/`.neq()` são no-ops no `QueryBuilder`.** `not(col, op, val)` empilha o filtro em `_filters`, mas `_buildParams()` só tem branch pra `eq/in/gte/lte/gt/lt/ilike` — nenhum `not_is`. `neq()` nem empilha nada, só retorna `this`. Backend (`crud.ts`) também não tem parâmetro equivalente a `_not_null`/`_ne` — implementar suporte genérico exigiria mudar os dois lados, usados por muitas tabelas, fora do escopo de um fix pontual. **Uso real confirmado e afetado:** `StepAntiBan` em `Disparos.tsx` (linha ~993) — `api.from("agentes").select("*").not("evolution_instancia", "is", null)` sempre trouxe TODOS os agentes do usuário, inclusive os sem instância Evolution conectada, como opção selecionável no seletor de instâncias do anti-ban. Se o usuário selecionasse só essas linhas "fantasma", o backend (`resolverInstanciasCampanha`, que filtra corretamente) devolveria lista vazia e o round-robin cairia num fallback de instância única, sem aviso nenhum — anulando a distribuição multi-instância. **🔧 Corrigido:** filtro aplicado no cliente (`.filter(i => !!i.evolution_instancia)`), isolado neste único ponto de uso — `client.ts` comentado com `[AUDITORIA] BUG`/`FIX PENDENTE` para não confiar em `.not()`/`.neq()` em código futuro sem implementar o suporte de verdade primeiro.

**Build:** `tsc --noEmit` limpo. **Deploy:** ainda pendente nesta entrada — ver `STATUS.md` para o que foi de fato enviado à VPS.

### 🔴 Bug real: chat ainda "puxava pra baixo" ao tentar ler mensagens antigas — causa raiz #2 encontrada (WhatsAppInterface.tsx, 2026-07-27)

**Contexto:** usuário reportou que o bug "ao subir pra ler mensagem antiga, o chat volta sozinho pro fim" continuava acontecendo. Investigação encontrou duas causas empilhadas, não uma:

**Achado 1 — fix de 2026-07-26 nunca commitado nem deployado.** `git diff` mostrou que uma sessão anterior (datada de comentários `[AUDITORIA] BUG ... 2026-07-26` já presentes no arquivo) já tinha implementado corretamente: (a) backend (`backend/src/routes/whatsapp.ts`, rota `GET /conversas/:phone`) — trocado `ORDER BY ASC + LIMIT/OFFSET` (bug pior, sempre retornava as mensagens MAIS ANTIGAS da conversa, nunca as recentes, numa conversa com >100 msgs) por `ORDER BY DESC + cursor "before"`, permitindo paginar pra trás de verdade; (b) frontend — `loadOlderMessages()` novo usando o viewport real do Radix ScrollArea (`[data-radix-scroll-area-viewport]`, o `ref` do componente aponta pro Root que nunca rola) em vez do `onScroll` no wrapper (que nunca disparava, evento `scroll` não borbulha). Essas mudanças existiam **só no working tree local**, nunca commitadas, nunca deployadas em homolog/produção — ou seja, o ambiente que o usuário testa continuava 100% no comportamento antigo, o que já explicaria o bug sozinho.

**Achado 2 — bug adicional, não coberto pelo fix acima, e que persistiria mesmo depois de deployar o Achado 1.** Um `useEffect` separado (linha ~1200) fazia `messagesEndRef.current?.scrollIntoView(...)` com `[activeChatId, chats]` nas dependências — ou seja, rodava incondicionalmente a CADA mudança de `chats`, que acontece a cada poll (3 intervals independentes, 2-5s cada, já documentados na Camada 4 mais acima no arquivo). Esse efeito não tinha nenhuma checagem de `isAtBottom`, então "vencia" por cima do gating que o fix de 07-26 já tinha aplicado dentro de `fetchMensagens` (`showLoading || isAtBottomRef.current`). Era este o efeito realmente puxando o usuário pra baixo enquanto tentava subir, em qualquer ambiente onde o código rodasse.

**🔧 Corrigido:** dependências do efeito reduzidas a `[activeChatId]` — o scroll ao ABRIR uma conversa já é coberto por `fetchMensagens(..., showLoading=true)` na troca de chat (mesma condição de gating), então este efeito agora só dispara na troca de conversa em si, nunca mais em resposta a um poll.

**Build:** frontend (`vite build` + `tsc --noEmit`) e backend (`swc`) limpos. **Nada disso está commitado nem deployado ainda** — commit e deploy (homolog primeiro) ficam para quando o usuário confirmar.

**Também revisado nesta sessão — botões decorativos catalogados (pedido explícito do usuário, "outros botões sem utilidade"):**
- Confirmados os 7 já documentados em sessões anteriores (5 no painel de detalhes — Abrir no CRM, + etiqueta, Ver tudo mídia, Ver todos documentos, editar anotações —, `runUITests` visível em produção, e o menu "Silenciar" já corrigido).
- **Novo — ícone de filtro (`SlidersHorizontal`, linha ~2025, header da lista de conversas):** sem `onClick`, não existe nenhum estado de filtro/ordenação no arquivo pra ligar. `FIX PENDENTE` (decisão de produto: filtrar por quê).

**Segunda passada — leitura completa do arquivo (pedido explícito do usuário: "continuar a varredura"), 4 achados novos além dos acima:**

- **🔴 CONFIRMADO E CORRIGIDO — crash em potencial no highlight de busca.** `highlightText()` (linha ~1833) montava `new RegExp(term, ...)` direto do que o usuário digita nas duas caixas de busca (busca global e busca na conversa), sem escapar metacaracteres de regex. Um termo bem plausível de digitar — ex: um telefone formatado `(11) 98888-7777` — ou quebra o highlight silenciosamente (parênteses viram grupo de captura em vez de caractere literal) ou, com um metacaractere desbalanceado (só `(` ou só `[`, fácil de acontecer no meio da digitação antes de fechar), lança `SyntaxError` dentro do render — sem error boundary acima disso, derruba a tela inteira do chat a cada tecla assim digitada. **Fix aplicado:** nova `escapeRegExp()`, aplicada antes de montar o padrão — comportamento de busca válido não muda, só passa a tratar o termo como texto literal.

### 🔴 Bug transversal — `.select()` após `.insert()`/`.update()` no cliente de API (2026-07-25)

**Contexto:** usuário reportou "Erro ao criar lista de importação" ao confirmar a importação de contatos em Disparos.tsx. **🔧 Corrigido — causa raiz real, afeta toda a aplicação, não só a importação.** `QueryBuilder.select()` (`src/integrations/database/client.ts`) sobrescrevia `_op` incondicionalmente pra `'select'`, mesmo quando chamado depois de `.insert()`/`.update()`. O padrão idiomático `api.from(t).insert(x).select().single()` (usado em `StepReview.handleStart` de `Disparos.tsx` pra criar campanha, na importação de CSV/XLSX pra criar lista, e em `ConfigAgenteIA.tsx`) perdia silenciosamente a operação de escrita: `_exec()` executava um `GET` sem filtro nenhum em vez do `POST` esperado. **Fix:** `.select()` só assume `_op='select'` quando ainda não há uma operação de escrita (insert/update/delete) em andamento — preserva o uso padrão isolado e corrige o encadeamento em toda a aplicação de uma vez. Build frontend sem erros. **Não testado em homolog ainda** (deploy pendente) — próximo passo é confirmar que a importação de Disparos e a tela de `ConfigAgenteIA` (que também tinha o mesmo padrão quebrado, possivelmente mostrando config errada silenciosamente até agora) funcionam corretamente após o deploy.

**🟠 Item 1 — mídia expirada em campanhas de múltiplos dias (implementado, escopo ampliado além do arquivo pedido).** O pedido citava `whatsapp.ts`/`/send`, mas o cenário descrito ("campanhas que rodem por múltiplos dias") na verdade vive em `disparoProcessor.ts` — `/send` é só envio manual avulso (uma mensagem, uma vez), quem reenvia o mesmo `url_midia` repetidamente ao longo de dias é o motor de campanhas. Implementado nos dois lugares com a mesma lógica compartilhada: nova `garantirMidiaEstavel()` em `whatsappMediaStorage.ts` — se a URL já é do nosso próprio domínio (`${API_BASE_URL}/uploads/...`, mesmo storage já usado por catalogo.ts/galeria.ts/elevenlabs.ts), devolve sem mexer; se for uma URL `http(s)://` externa, baixa uma vez e persiste em `UPLOADS_DIR` (público), devolvendo uma URL própria que nunca expira. Falha no download nunca bloqueia o envio — cai de volta pra URL original (mesma filosofia de fallback já usada pra mídia de entrada). Em `disparoProcessor.ts`: estabiliza uma vez por campanha por lote (cache em memória `urlMidiaEstavelPorCampanha`) e persiste de volta em `disparos.url_midia` — a partir daí, mesmo dias depois, `get_next_disparo_batch()` já devolve a URL estável direto, sem recachear. Em `whatsapp.ts`: aplicado em `POST /send` antes de montar o payload da Evolution, e o `media_url` salvo em `whatsapp_messages` reflete a URL final estável (evita o mesmo problema reaparecer na visualização do histórico do chat).

**🟠 Item 2 — teto de 5MB contra Heap OOM em POST /send (implementado).** `mediaUrl` pode chegar como URL `http(s)://` OU como data-URI base64 embutido direto no corpo JSON (que aceita até 50MB, ver `index.ts`) — o segundo caso é o risco real de OOM (string+Buffer gigante em memória por request concorrente). Duas camadas: (a) base64 — calcula o tamanho aproximado a partir do comprimento da string (`length * 0.75`) e barra com `413` antes de qualquer processamento, sem decodificar nada; (b) URL externa — checagem best-effort via `HEAD`/`Content-Length` antes de deixar seguir; o teto real e definitivo é reforçado dentro de `garantirMidiaEstavel()` (mesma constante `MAX_OUTBOUND_MEDIA_BYTES`, compartilhada com o item 1), que descarta e cai pro fallback se o arquivo baixado passar de 5MB — cobre também o caminho de campanhas em `disparoProcessor.ts`, que não tem uma requisição HTTP pra devolver 413, mas se beneficia do mesmo teto no download.

### 🟠 Sprint 5 — Blindagem do motor de disparos em lote (disparoProcessor.ts, migrations.ts, cron.ts) (2026-07-23)

**Contexto:** kickoff explícito do usuário, 3 blindagens pontuais no motor de disparos em lote (Bulk Messaging), parte do roteiro "[MÓDULO WHATSAPP & INTEGRAÇÃO EVOLUTION API]" (Sprint 5 de 9).

**🟢 Item 1 — disparo em duplicidade sob múltiplas réplicas (JÁ estava correto, só verificado).** Pedido: garantir `FOR UPDATE SKIP LOCKED` na função `get_next_disparo_batch`. Confirmado lendo `migrations.ts` que essa função já usa exatamente esse padrão — uma CTE com `SELECT ... FOR UPDATE SKIP LOCKED` combinada com `UPDATE ... FROM` no mesmo statement (transação implícita única), o idioma padrão do Postgres pra fila de trabalho concorrente. Duas réplicas do backend chamando a função ao mesmo tempo nunca recebem a mesma linha. Nenhuma mudança de código necessária; documentado com `[AUDITORIA] LÓGICA` pra não reabrir a dúvida numa sessão futura.

**🟠 Item 2 — retries com backoff para quedas temporárias da Evolution (implementado).** Antes, qualquer erro (502 passageiro, timeout de rede, número inválido, 4xx) marcava o log como `failed` direto — a coluna `tentativas` (já existia no schema, default 0) nunca era lida nem incrementada. Erro permanente (4xx, payload inválido) continua indo direto pra `failed`, sem retry. Retries não contam pro circuit breaker de erros consecutivos (anti-ban) nem inflam `disparos.falhas` antes da hora — só falha definitiva conta como "erro" pra esses dois mecanismos. O delay antiban entre mensagens (5-60s conforme perfil de velocidade) continua se aplicando mesmo após um retry, de propósito — não bater mais rápido na Evolution logo quando ela está instável.

**🟡 Item 3 — teto diário de segurança / salvaguarda antiban (implementado).** Antes de processar a primeira mensagem de cada campanha dentro de um lote, `disparoProcessor.ts` agora conta `disparo_logs` com `status='sent'` nas últimas 24h corridas por `user_id` (dono da campanha), contra um teto configurável por campanha (`disparos.limite_diario_mensagens`, novo, default 500 — mesmo padrão já usado por `limite_erros_consecutivos`). Ao exceder, pausa a campanha (`status='pausado'`, `aviso='Limite diário de segurança atingido. Retomando automaticamente amanhã.'`, `pausado_motivo='limite_diario'`, `pausado_em=NOW()`) e reenfileira toda mensagem já claimada ('sending') dessa campanha no lote atual (rastreado via `campanhasPausadasNesteLote`, evita que o loop continue enviando mensagens da campanha recém-pausada só porque elas já vieram no mesmo lote). Implementado também o auto-resume prometido no próprio texto do aviso — nova função SQL `reativar_disparos_por_limite_diario()` + cron a cada 5min (`cron.ts`) que reativa campanhas pausadas especificamente por esse motivo depois de 24h, sem tocar em pausa manual nem em pausa por erros consecutivos (que pode ser sinal de bloqueio real e exige revisão humana).

**Limitação documentada (`FIX PENDENTE`):** o teto é por `user_id` inteiro, não por instância/chip individual — `disparo_logs` não registra qual instância Evolution enviou cada mensagem, só o dono da campanha. Separar por número exigiria adicionar uma coluna `instancia` em `disparo_logs` (preenchida no envio real), relevante agora que multi-instância existe (um tenant pode ter vários números, cada um com seu próprio risco de banimento). ### 🔧 Sprint 1 (roteiro reformulado): fix ON CONFLICT em `contatos`, auditoria de RLS dormente, e diagnóstico de `agent_configs`/n8n.ts (2026-07-22)

**Item 1 — `ON CONFLICT` no upsert antecipado de contato (`webhook.ts`):** toda mensagem recebida gerava `"there is no unique or exclusion constraint matching the ON CONFLICT specification"` (visto ao vivo no monitor de logs, durante a conversa de teste entre os dois números). ### 🔴 INCIDENTE REAL (2026-07-22) — bypass de admin no CRUD genérico misturava/expunha dados de todos os tenants

**Origem:** investigando por que `InstanceManagementPanel.tsx` (painel de Instâncias WhatsApp) mostrava, pra uma conta admin, a instância de outro usuário misturada com a própria — o mesmo tipo de confusão que muito provavelmente causou o incidente anterior desta sessão (admin excluiu o WhatsApp de outro cliente por engano, ver entrada abaixo).

**Causa raiz:** `backend/src/crud.ts` (factory `makeCrud()`, usada por praticamente todo CRUD simples do sistema) tinha um bypass incondicional — `resolveUserId()` retornava `null` pra qualquer request com `role === 'admin'`, fazendo `buildWhere()` nunca adicionar `WHERE user_id = $1`. Isso valia pra **toda** tabela montada com `makeCrud()` sem exceção: `GET` lista, `PUT/DELETE /:id`, e updates/deletes em lote (`PUT /`/`DELETE /` com filtros de query string). Agravante: `src/integrations/database/client.ts` descarta silenciosamente qualquer `.eq('user_id', ...)` que um componente tente passar (linha ~316), então nenhuma tela conseguia se proteger sozinha chamando esse filtro "com mais força" — a proteção só podia vir do backend.

**Varredura com agente de classificação em 13 arquivos** que tinham esse padrão encontrou vazamento de leitura em 10 telas "pessoais" (`Agentes.tsx`, `Campanhas.tsx`, `CentralBI.tsx`, `Cerebro.tsx`, `Configuracoes.tsx`, `Discagem.tsx`, `Leads.tsx`, `PromptAgente.tsx`, `SetupAgente.tsx`, `SLA.tsx` — todas em rotas `requireModulo`, acessíveis a qualquer usuário comum, não `requireAdmin`) e **dois bugs de escrita real, mais graves**:
- `PromptAgente.tsx`: "desativar prompt atual" virava `PUT /api/agent_prompts?ativo=true` sem filtro de usuário como admin — desativaria o prompt ativo de **todos os tenants** de uma vez.
- `SetupAgente.tsx`: limpeza de conhecimento virava `DELETE /api/conhecimento?tipo_in=negocio,personalidade,script` sem filtro de usuário — apagaria essas linhas de **todos os tenants**.
- `SetupAgente.tsx` e `SLA.tsx` também sobrescreviam (`PUT /agentes/:id`) a linha `agentes` — credenciais/webhook da Evolution — de outro tenant, quando um admin salvava.

`UsuariosAcessos.tsx` foi a única exceção legítima (rota `requireAdmin`, tabela `user_roles` com rotas próprias já gateadas por `adminMiddleware`, nunca passou por `makeCrud`).

**🔧 Corrigido:** bypass de admin em `crud.ts` virou opt-in explícito por tabela (`adminBypass?: boolean`, default `false`). Auditado todo `makeCrud()` do backend (mounts diretos em `index.ts` + os que os routers especializados — `agent_prompts.ts`, `contatos.ts`, `disparos.ts`, `documents.ts`, `n8n_chat_histories.ts` — criam internamente): nenhuma tabela precisa do bypass hoje, então nenhuma recebeu `adminBypass: true`. Fix de arquivo único no backend — não precisou tocar em nenhum dos 12 arquivos de frontend.

**Verificado em homologação** com 2 contas de teste descartáveis (uma promovida a admin via `UPDATE users SET role='admin'`, só pra teste) e dados plantados pra uma "vítima": confirmado que como admin — `GET` lista não inclui mais linhas de outro usuário, `PUT/DELETE /:id` numa linha alheia retorna 404 sem alterar nada, e os dois bugs de escrita em lote (deactivate-all do `agent_prompts`, delete-by-tipo do `conhecimento`) agora afetam 0 linhas e não tocam os dados da vítima. Usuário comum: zero mudança de comportamento (já era corretamente escopado antes). Deploy em produção confirmado saudável (tráfego real de webhook e navegação do admin real, sem erros).

**Pendências relacionadas, fora de escopo desta correção:**
- `agent_configs` (usado por `ConfigAgenteIA.tsx`) não está montado como `/api/agent_configs` — só existe `/api/agent-config` (hífen) — rota 404 pra todo mundo hoje, bug de roteamento diferente, não mexido.
- `funil_estagios` (usado por `Funil.tsx`) nunca teve filtro de `user_id`, nem no frontend — como é `SIMPLE_TABLES`/`makeCrud` padrão, o fix acima já o escopa automaticamente como efeito colateral, mas vale confirmar depois se "estágios de funil pessoais por usuário" é o comportamento de produto desejado ou se deveria ser compartilhado por conta/equipe.

### 🔧 Piloto de RLS (Row-Level Security) em `whatsapp_messages` — só homologação (2026-07-22)

**Contexto:** item pendente listado na sessão anterior ("RLS como rede de segurança contra futuros bugs de escopo"). Escolhido pelo usuário como próximo passo, com instrução explícita: fazer tudo em homologação, garantir zero impacto em produção, subir todos os commits pendentes antes de começar (verificado: 0 pendentes).

**Achado crítico que redesenhou o plano:** a role `mentoark`, usada por toda a aplicação hoje (produção e homolog), é **superuser do Postgres** (`rolsuper=t, rolbypassrls=t`). Superusers ignoram RLS incondicionalmente, mesmo com `FORCE ROW LEVEL SECURITY`. Simplesmente habilitar RLS nas tabelas não teria efeito nenhum enquanto a app conectasse como `mentoark` — seria uma falsa sensação de segurança. Também descoberto: já existiam 2 políticas RLS órfãs no banco (`chat_messages_user_policy`, `agent_configs_user_policy`, usando `auth.uid()` do Supabase — função que não existe neste backend Express+JWT), criadas manualmente no banco em algum momento, nunca commitadas, e sem efeito real justamente por causa do superuser.

**🔧 Implementado (só em `crm_hml`, banco e ambiente de homologação):**
1. Nova role `crm_app_hml` (não superuser, não bypassrls, não dona das tabelas) — é o que torna o RLS real em vez de teatro.
2. `backend/src/db.ts`: `migrationsPool` separado do pool da aplicação — migrations (DDL) continuam rodando com a role administrativa via `DATABASE_URL_MIGRATIONS`; a app passa a conectar via `DATABASE_URL` com a role restrita. Se `DATABASE_URL_MIGRATIONS` não estiver definida (caso de produção, hoje e sempre), cai para `DATABASE_URL` — comportamento idêntico ao de antes, zero mudança em produção.
3. `backend/src/middleware.ts`: novo `tenantContextMiddleware` — adquire um client dedicado do pool por requisição (lazy, só quando a rota chama `req.getDb()`), `SET LOCAL app.user_id`/`app.is_admin`, commit/rollback automático no fim da resposta. `req.setDbUserId()` para rotas que filtram por `tenantId` (dono de equipe) em vez do `userId` bruto do JWT.
4. `backend/src/db.ts`: `withTenantContext()` — mesma lógica para código fora do ciclo HTTP (webhook.ts, agentEngine.ts, disparoProcessor.ts, cron.ts).
5. RLS habilitado só em `whatsapp_messages` (piloto, a tabela do incidente de vazamento já documentado nesta sessão): policy `USING/WITH CHECK (app.is_admin = 'true' OR user_id = app.user_id)`.
6. Migrados todos os pontos de acesso a `whatsapp_messages` nos arquivos que a tocam: `routes/whatsapp.ts` (12 pontos), `routes/webhook.ts` (5 pontos, com bypass admin nos handlers sem userId resolvido), `routes/suporte_copiloto.ts` (1 leitura), `services/agentEngine.ts` e `services/disparoProcessor.ts` (INSERTs), `index.ts` (`/api/admin/webhook-trace`, bypass admin), `cron.ts` (expurgo de 90 dias, bypass admin — é cross-tenant por design). `routes/suporte.ts` e `services/suporte.ts` verificados como código morto (não importados em `index.ts`) — não fazem parte da aplicação em execução, pulados.
7. `.env`/`docker-compose.yml` de `crm-api-homolog`: `DATABASE_URL` trocado pra `crm_app_hml`, `DATABASE_URL_MIGRATIONS` adicionado com a connection string antiga (`mentoark`). Backups salvos (`.bak_pre_rls_2026-07-22`). Rebuild + restart só do `crm-api-homolog` — `crm-api` (produção) não foi tocado (confirmado: uptime contínuo de 12h antes/depois, sem restart).

**✅ Verificação (suite completa, com 2 usuários descartáveis criados via `/auth/register` — nenhum dado de cliente real usado, tudo apagado ao final):**
- Positivo: usuário de teste A viu só a própria conversa/mensagem; usuário B idem; busca (`GET /search`) de B por um termo presente na mensagem de A não retornou nada de A.
- Bloqueio via `psql` direto como `crm_app_hml` (não `mentoark`): sem `app.user_id` setado → 0 linhas. Com `app.user_id` de um tenant aleatório → 0 linhas.
- **Teste decisivo (prova que a rede de segurança funciona mesmo com bug de código):** `SET app.user_id` do tenant B e rodar `SELECT * FROM whatsapp_messages` **sem nenhum `WHERE user_id`** (simulando um bug de escopo esquecido, a mesma classe dos incidentes reais já documentados nesta sessão) → RLS filtrou sozinho, só devolveu a linha do próprio tenant B. `UPDATE` tentando alterar a mensagem do tenant A autenticado como tenant B, também sem `WHERE user_id` → `UPDATE 0`, bloqueado pelo `WITH CHECK`.

### 🔴 INCIDENTE REAL (2026-07-21) — perda de mensagens ao deletar uma instância WhatsApp, backend/src/routes/whatsapp.ts

**O que aconteceu:** durante a investigação do bug P2010 (ver seção "Infra — Evolution API" abaixo), o usuário deletou pela tela do CRM uma instância órfã (`crm_a5d1255fce86`, diferente da instância real em uso). **Confirmado nos logs de produção:** 5 mensagens reais (trocadas horas antes durante os testes do P2010, instância `crm_435ee4720fc3`, número `5511991909106`) foram apagadas de `whatsapp_messages` no exato momento em que `crm_a5d1255fce86` foi deletada — comprovado comparando duas leituras da tabela antes/depois e cruzando com os logs de `DELETE /api/whatsapp/instances/crm_a5d1255fce86` (`200 OK`, mesmo `userId` das mensagens perdidas).

**Recomendação para o futuro:** considerar soft-delete (coluna `deleted_at` em vez de `DELETE` físico) em `whatsapp_messages`, e configurar rotina de backup do Postgres (`pg_dump` agendado via cron) — hoje não existe nenhuma, qualquer bug de escopo como este é permanente e sem chance de reversão.

### Infra — Evolution API (2026-07-21) — bug P2010 (mensagens recebidas não chegam ao CRM): investigado, fix tentado e revertido, causa raiz refinada

**Contexto:** bug conhecido desde 2026-07-08/10 (ver seção "Rastreio mensagens novas não atualizam" mais abaixo neste arquivo) — Evolution API v2.3.7 quebra internamente em `updateChatUnreadMessages()` (chamado a partir de `messages.upsert`) antes de conseguir despachar o webhook, então o CRM nunca recebe mensagens genuínas de WhatsApp. Confirmado ainda ativo em produção em 2026-07-21 (teste ao vivo, número real, 0 eventos `messages.upsert` em 72h de log).

**Nova informação encontrada nesta sessão:** o erro real alterna entre duas variantes, ambas dentro do código `P2010` do Prisma:
1. `Code: 1064` — `You have an error in your SQL syntax ... near '"Message"'` — erro de sintaxe MySQL genuíno: a query usa aspas duplas para identificador (`"Message"`), válido em PostgreSQL, **inválido em MySQL** (que usa crase por padrão). Forte indício de que a raw query foi escrita para Postgres e nunca adaptada corretamente para MySQL.
2. `Error querying the database: Named and positional parameters mixed in one statement` — incompatibilidade de binding de parâmetros do Prisma especificamente contra MySQL.

Encontrado no upstream (`github.com/evolution-foundation/evolution-api`) o PR #2333 ("fix(mysql): compatibilidade da coluna lid e queries RAW", merged 2026-02-24 em `develop`) que reescreve exatamente `updateChatUnreadMessages()` com versões MySQL dedicadas — mas **não há release estável desde v2.3.7** (2025-12-05); só existem prereleases `2.4.0-rc1` (2026-05-06) e `2.4.0-rc2` (2026-05-17), lançadas depois desse PR.

**Tentativa de fix, revertida:** atualizamos `evolution` (VPS) de `evoapicloud/evolution-api:latest` (= v2.3.7, imagem local cacheada há 2 meses, não recebia atualização automática) para `2.4.0-rc2`. Resultado: **P2010 resolvido** (mensagem real recebida e salva em `whatsapp_messages` com sucesso, confirmado no banco) — mas **toda a API REST da Evolution passou a exigir licença paga** (`{"code":"LICENSE_REQUIRED"}` em qualquer chamada, inclusive `fetchInstances` e `sendText`), quebrando o **envio** de mensagens (motor de disparo e chat manual) em produção. Testado também `2.4.0-rc1` — mesmo bloqueio de licença. **Ambos revertidos**, confirmado envio e recebimento restaurados ao comportamento anterior (send OK / receive com P2010).

**Ação de blindagem aplicada:** `image:` em `/opt/evolution/docker-compose.yml` fixado explicitamente em `evoapicloud/evolution-api:v2.3.7` (era `:latest`, uma tag flutuante) com comentário `[AUDITORIA]` documentando o bloqueio de licença do 2.4.x — evita upgrade acidental para uma versão paga sem essa informação, e evita que o `:latest` "ande sozinho" se o publisher atualizar o ponteiro no futuro.

**Segunda tentativa (mesma sessão), também revertida:** migrado `DATABASE_PROVIDER` do Evolution (v2.3.7, sem tocar em licença) de `mysql` para `postgresql`, usando um banco `evolution` novo e isolado no Postgres já existente da VPS (`postgres:5432`, mesma rede `proxy` que `evolution` — confirmado antes de migrar). Migrations internas do Prisma rodaram limpo contra o schema Postgres (`prisma/postgresql-schema.prisma`), sem nenhum erro de sintaxe — **confirma a hipótese do dialeto** (a v2.3.7 tem schema/queries Postgres nativas; o bug só aparece porque a instalação estava rodando contra MySQL). Porém: o banco novo fica vazio (sem as linhas da tabela `Instance`), e o Evolution **não religa instâncias automaticamente sem esse registro** — mesmo com os arquivos de sessão do Baileys intactos em `/evolution/instances/<id>/` no volume. Resultado: `fetchInstances` retornou `[]`, instância real (`crm_435ee4720fc3`) desaparecida da API — queda total (envio E recebimento), pior que a trava de licença da tentativa anterior. Revertido imediatamente para MySQL, confirmado envio funcionando de novo.

**Terceira tentativa (mesma sessão), incidente real — sessão de WhatsApp deslogada:** com os nomes de coluna corrigidos e dados de `Instance`/`Setting` migrados manualmente e verificados (5 linhas cada, ids preservados, booleans convertidos corretamente 0/1→false/true), a injeção funcionou tecnicamente — `fetchInstances` voltou a listar as 5 instâncias com metadados corretos. **Porém:** ativar `DATABASE_ENABLED=true` não é só uma troca de metadados — faz o Evolution migrar o armazenamento da sessão do Baileys (credenciais de pareamento) de **arquivo** (`/evolution/instances/<id>/`, que ficou intocado o tempo todo) para a **tabela `Session` do Postgres**, que fica vazia no schema novo (e é recriada/limpa de novo pelo `TRUNCATE ... CASCADE` em `Instance`, que já tínhamos visto cascatear pra `Session` no teste anterior). Resultado: a instância real (`crm_435ee4720fc3`) gerou um **QR code novo**, e o WhatsApp, ao detectar uma tentativa de pareamento duplicado no número já linkado, **deslogou a sessão de verdade no lado do WhatsApp** (log: `state: close, statusReason: 401` → `WAMonitoringService: LOGOUT` → `REMOVED`). Revertido o `docker-compose.yml` para MySQL imediatamente, mas isso **não desfez o logout** (já tinha acontecido no protocolo do WhatsApp, não é um estado só do nosso backend) — a instância ficou em `connectionStatus: close`/`connecting` mesmo após reverter. **O usuário precisou reconectar manualmente a instância** (novo pareamento) para restaurar o envio/recebimento; confirmado funcionando depois, com um `instanceId` novo gerado pelo Evolution (o vínculo antigo foi definitivamente invalidado).

**Estado atual:** recebimento de mensagens **continua quebrado** (P2010); envio restaurado, mas via uma sessão de WhatsApp inteiramente nova (não a mesma de antes). Banco `evolution` no Postgres removido novamente (não usado, dados agora obsoletos já que o `instanceId` mudou).

**Conclusão sobre a migração para Postgres:** tecnicamente resolve o P2010 (dialeto confirmado repetidas vezes), mas **exige re-pareamento do número real** — ativar `DATABASE_ENABLED=true` troca o mecanismo de auth-state do Baileys de arquivo para a tabela `Session` do Postgres, e essa troca não preserva a sessão existente independente de qualquer cópia manual de dados de `Instance`/`Setting`. Não é um bug contornável — é como a Evolution v2.3.7 implementa a troca de provider.
